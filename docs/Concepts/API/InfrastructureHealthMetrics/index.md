# Infrastructure Health Metrics

[Application Log Entry](../ApplicationLogEntry/index.html) captures problems as they are logged. Infrastructure Health Metrics is the complementary, always-on, evaluation picture, which is to say a per-minute snapshot of the shared infrastructure upon which a Jube instance depends: the .NET runtime in which it is running, the Postgres database to which it is storing, the Resp cache from which it is reading and to which it is writing (Garnet being the primary server, with any Redis-compatible server being supported), the Patroni and etcd orchestration layer managing Postgres high availability when present, and the Docker host (or hosts) on which it is actually running (via the standalone [Jube.Monitoring](#docker-monitoring-sidecar-jubemonitoring) sidecar). Taken together, it follows that diagnosing an incident rarely requires shelling into a node or a database server.

Nothing needs configuring for the .NET, Postgres and Resp tables, as sampling starts with the engine and runs regardless of whether any Model is active, on a dedicated background thread independent of the per-Model counter flush. The etcd and Patroni sampling additionally tries to discover endpoints on its own (see [etcd and Patroni](#etcd-and-patroni) below), and explicit configuration is only needed if that guesswork does not match the topology of a given deployment. Keeping in mind that Jube maintains a Docker Swarm Reference Cluster, the monitoring leans towards providing full coverage for that topology.

This page is specifically about the *shared infrastructure* upon which Jube depends. The Archiver and case creation pipelines, being the background work of Jube itself rather than a dependency, are given the equivalent per-minute rollup and warn-threshold capture treatment in [Background Processing Performance](../BackgroundProcessingPerformance/index.html), including the `CaptureQueueHealth` table that reports on the `RespSentinelEvent` and `RespConnectionEvent` capture queues of this page alongside those of the two pipelines.

## What is captured

The tables are grouped below by the subsystem that each watches. The .NET runtime, Postgres and the Resp cache all report on themselves, whereas Patroni, etcd and Docker need a fundamentally different approach, each being covered in its own section further down. Most of these are wide tables, having one row per instance per minute with a broad, fixed set of columns, rather than one row per named metric, since each surface exposes a fixed, well-known metric set that is far easier to chart and correlate as a wide row than to reassemble from many narrow ones. A handful are instead narrow tables of one row per event, where the underlying thing being captured is itself discrete (a slow command, a connection event, a Sentinel message) rather than a snapshot of an always-present value, and each is called out as such below.

### The .NET runtime

- **`DotNetRuntimeMetric`**: GC generation counts, allocated, heap and fragmented bytes, memory load, working set and private memory, thread count, ThreadPool worker and IO thread availability and configured maximums, ThreadPool queue length, and cumulative CPU time. It is sampled entirely from in-process APIs (`GC`, `ThreadPool`, `Process`), there being no connection of any kind, and it follows that it can never itself fail to reach a dependency.

  This is also where container-level CPU and memory visibility live, split across two independent sources depending on what needs no special access at all, versus what needs the Docker socket that the Monitoring sidecar alone holds:
    - **`RuntimeAvailableMemoryBytes`** / **`RuntimeCommittedMemoryBytes`**: the view that the .NET GC has of its own memory budget, which has been container-limit-aware since .NET Core 3.0 (it already reads the same cgroup limit as below, hence this is a free, built-in confirmation of what the runtime believes it can use).
    - **`GcPauseTimeMicroseconds`** / **`LockContentionCount`**: cumulative GC pause time and lock-contention count (`GC.GetTotalPauseDuration()` and `Monitor.LockContentionCount`), being the two most common causes of "the process is up but slow" that neither the container nor the Postgres and Resp metrics could ever reveal.
    - **`ContainerCpuLimitCores`**, **`ContainerCpuUsageMicroseconds`**, **`ContainerCpuThrottledPeriods`**, **`ContainerCpuThrottledMicroseconds`**, **`ContainerMemoryLimitBytes`**, **`ContainerMemoryUsageBytes`**: read directly from the cgroup pseudo-files of the container itself under `/sys/fs/cgroup` (cgroup v2, falling back to v1), which are visible to any process inside the container without any Docker API access at all. `ContainerCpuThrottledPeriods` and `ContainerCpuThrottledMicroseconds` in particular are the direct answer to "is the CPU limit of the orchestrator actually throttling the process", where non-zero and climbing means that the container is CPU-starved by its own configured limit, not by host contention. All six are null when not running inside a container (or when the cgroup pseudo-files are not reachable for some other reason), never zero, hence a null reliably means "not applicable" rather than "no throttling happened". True Docker and Swarm level visibility of that same container, of the kind that only the daemon itself can see, is a separate concern entirely, covered under [Docker Monitoring Sidecar](#docker-monitoring-sidecar-jubemonitoring) below.

### Postgres

- **`PostgresMetric`**: active connections, cumulative transaction, row, temp-file, deadlock and conflict counters (the `pg_stat_database` counters of Postgres itself, stored as they are each interval so that a query can diff between rows for a rate), a derived cache-hit-ratio percentage (computed from the delta since the previous sample, such that it reflects recent behaviour rather than the lifetime average), replication status (`IsInRecovery`, `ReplicationLagSeconds`, `ReplicaCount`), on-disk database size (`DatabaseSizeBytes`), the single longest-running active query in seconds (`LongestRunningQuerySeconds`, null when nothing is active), backends currently waiting on a lock (`WaitingBackends`), and cumulative WAL bytes generated (`WalBytesGenerated`, from `pg_current_wal_lsn()`, or `pg_last_wal_receive_lsn()` on a replica).
- **`PostgresReplicationStatus`**: one row per connected standby per one-minute sample, read directly from `pg_stat_replication` on the primary: `Pid`, `UserName`, `ApplicationName`, `ClientAddress`, `State`, the four LSN positions (`SentLsn`, `WriteLsn`, `FlushLsn`, `ReplayLsn`), the three lag measures (`WriteLagSeconds`, `FlushLagSeconds`, `ReplayLagSeconds`), and synchronous-replication state (`SyncState`, `SyncPriority`). `PostgresMetric` above only carries the aggregate (the maximum lag across every replica), whereas this is the per-replica detail behind it, read directly from the native replication view of Postgres, with or without Patroni managing the cluster. It is empty on a standby, or on a primary with no connected replicas.

The server log of Postgres itself, and its live activity and blocking view, are topics large enough to earn their own sections further down, as set out in [Postgres's own server log](#postgress-own-server-log-postgreslogentry) and [Live activity and blocking](#live-activity-and-blocking-get-apipostgresactivity) below. Table and index level DBA statistics (`PostgresTableStatistics` and `PostgresIndexStatistics`) are a related but distinct concept, being live catalogue queries and not per-minute history, and are documented in their own page, [Postgres Database Statistics](../PostgresDatabaseStatistics/index.html).

### Redis

The tables in this section carry the `Resp` prefix, Resp being the wire protocol that Garnet and Redis share, and they are populated from whichever Resp server the `RespConnectionString` Environment Variable points at. The samplers are written against the protocol through the StackExchange.Redis client (`INFO`, `SLOWLOG` and, where configured, the Sentinel commands) with no branch that is particular to one server, and it follows that a field which a given server does not report in its `INFO` reply is stored as zero, false or null rather than failing the sample. Sentinel is a facility of Redis only, hence the two Sentinel tables stay empty when Garnet is the server.

- **`RespMetric`**: connected and blocked clients, memory usage and configured maximum, operations per second, cumulative commands, connections, evictions and expirations, a derived keyspace hit-rate percentage (using the same delta-based technique as the cache-hit ratio of Postgres), replica count, replication offset, uptime, total key count across every logical database (`TotalKeys`), memory fragmentation ratio (`MemoryFragmentationRatio`), age of the last successful RDB snapshot (`RdbLastSaveAgeSeconds`), and whether AOF persistence is on (`AofEnabled`). It also carries the absolute UTC timestamp of the last successful RDB background save (`LastBgSaveDate`, sometimes called a "background copy", read directly from the `rdb_last_save_time` field of the `INFO` reply) and of the last completed AOF rewrite (`LastAofRewriteDate`), where comparing the two flags up the fork contention that happens when a BGSAVE and an AOF rewrite overlap, since both fork the server process and compete for the same copy-on-write memory. The `INFO` reply exposes no absolute timestamp of the last AOF rewrite (only the duration of the most recent one), hence `RespMetricSampler` derives it by watching `aof_rewrites` (a monotonic counter) advance between samples and stamping that moment, and it follows that `LastAofRewriteDate` is null until the first rewrite is observed after the sampler starts, even if earlier rewrites happened before then.
- **`RespSlowOperation`**: a narrow table dumping the slow-command log of the server itself, with one row per `SLOWLOG` entry: `RespSlowLogId` (the monotonic sequence number of the server, used to avoid inserting the same entry twice across consecutive one-minute samples of the same rolling buffer), `OccurredDate`, `DurationMicroseconds`, the command and its arguments (`Command`), the command verb pulled out of it (`CommandName`, e.g. `SET`, `HGETALL`) so that slow commands can be grouped by type, a best-effort key name (`KeyName`, which is not meaningful for multi-key or scripted commands such as `MSET` or `EVAL`), and the address and name of the issuing client (when the server reports them).
- **`RespConnectionMultiplexerMetric`**: different from the two tables above in one important way, being sampled from the live connection of the application itself and not a dedicated diagnostic one. It is a per-minute snapshot of the actual production `ConnectionMultiplexer` of `Jube.Cache.CacheService` (the one through which every cache read and write in the engine passes), covering both its interactive (command) connection and its subscription (pub/sub) connection: connected and connecting status, endpoint count, cumulative operation count, and for each connection type its **queue depth**, which is to say `PendingUnsentItems` (queued but not yet sent), `SentItemsAwaitingResponse` (sent, waiting on the server) and `ResponsesAwaitingAsyncCompletion` (received, waiting on the client), together with cumulative completed and failed operation counts and socket count. A climbing queue depth here means that the Resp server (or the network path to it) is not keeping up with the application, and it shows up here before it shows up as elevated invocation response times. It also carries counts of the diagnostic events of the multiplexer itself (`ConnectionFailedCount`, `ConnectionRestoredCount`, `ErrorMessageCount`, `InternalErrorCount`, `ConfigurationChangedCount`, `ConfigurationChangedBroadcastCount`), which otherwise reach only log4net. Unlike the queue-depth and operation-count columns above, these six are **per-minute counts, not cumulative**: each is atomically read and reset to zero at sample time (`RespConnectionDiagnosticsCounters.TakeSnapshot()`), such that the value of a row is "how many of this event happened in that one minute" and not a running total since process start, the question being answered is whether one tripped, and when. A Sentinel-driven failover typically shows up as a jump in `ConfigurationChangedBroadcastCount` in exactly the minute in which it happened.

  A count only ever answers "did one trip", and it necessarily discards which endpoint, which connection, and what actually failed. **`RespConnectionEvent`** is the detail behind it: the event handlers of `CacheService` capture every individual `ConnectionFailed`, `ConnectionRestored`, `ErrorMessage`, `InternalError`, `ConfigurationChanged` and `ConfigurationChangedBroadcast` occurrence (mirroring the capture-queue-and-bulk-flush shape of `RespSentinelEvent` below) into `EventType`, `EndPoint`, `ConnectionType` (Interactive or Subscription, when applicable), `FailureType`, `Origin` (InternalError only), `Message` (ErrorMessage only) and `Exception` (the full exception text, when the event carried one). Every captured event is also logged at Error or Warn, hence it reaches `ApplicationLogEntry` too, and `RespConnectionEvent` is the structured, per-event view of the same information, independent of whether Sentinel is in use.

  `RespConnectionEvent` also carries a seventh `EventType`, **`ReconnectRetry`**, that none of the six above raise. `CacheService` configures `ConfigurationOptions.ReconnectRetryPolicy` with `RespReconnectRetryPolicy`, a thin wrapper around the real `ExponentialRetry` policy that observes, rather than changes, every call that the StackExchange.Redis multiplexer makes to `ShouldRetry` while disconnected, that being the exact point at which the exponential backoff is decided. Each time the wrapped policy says that a retry is actually due (as distinct from the more frequent "not yet" calls made while still waiting out the backoff), it captures one row with `RetryCount` (which attempt this is, 1-based, since the connection entered the connecting state), `BackoffMilliseconds` (how long the backoff before this attempt actually was) and `TransactionsImpacted` (a snapshot of `Jube.Cache.Observability.CacheDiagnostics.InFlightCallCount`, being how many cache calls, across every repository, were awaiting completion at that instant, which is to say how many transactions the outage was stalling). This is what turns "the cache went away for a while" into "it took N retries growing to M ms apart, stalling as many as K in-flight calls at the worst point", the retry, backoff and impact story that a bare pair of `ConnectionFailed` and `ConnectionRestored` cannot tell on its own.
- **`RespCallCounter`**: one row per distinct `Call` label (a `Jube.Cache.Resp` repository method, e.g. `"CachePayloadRepository.InsertAsync"`, never a cache key or value) per one-minute window, with `Count`, `TotalMicroseconds`, `MinMicroseconds` and `MaxMicroseconds` for every call to that label during the window. This is the dedicated, reset-each-minute counterpart to the live `jube.cache.resp.call.count` and `jube.cache.resp.call.duration` OpenTelemetry instruments of `CacheDiagnostics`, having the same source (`CacheDiagnostics.Record`, called from the `RecordAsync` or `Record` wrapper of every repository method) and the same `Call` label, but accumulated in `Jube.Cache.Observability.CacheCallCounters` (a global `ConcurrentDictionary<string, Accumulator>`, not per-model, since cache calls are not scoped to any one `EntityAnalysisModel`) and read-and-reset once a minute by the sampling group covering it (see [Sampling architecture](#sampling-architecture-fan-out-join-and-opentelemetry) below), in the manner of the `Interlocked.Exchange` idiom that `ManageCountersStarter` already uses for the per-model Task, Stage and Response Time Pipeline counters. It answers, directly and without needing an external OpenTelemetry collector, exactly where cache load is coming from by area of the system: which repository method, how often, and how slow.
- **`RespSentinelStatus`**: one row per entity (`master`, `slave` or `sentinel`) reported by `SENTINEL MASTERS`, `SENTINEL SLAVES` and `SENTINEL SENTINELS` per one-minute sample, taken over the same Sentinel connection that `Jube.Cache.CacheService` already holds when `RespConnectionString` configures a `ServiceName`: `EntityType`, `Name`, `Ip` and `Port`, `Flags` (the state flags of Sentinel itself, where `s_down`, `o_down` and `failover_in_progress` are the ones to watch for), and, for slave rows, `MasterLinkStatus`, `MasterHost`, `MasterPort` and `SlaveReplOffset`. It is only populated when Sentinel is actually in use.

  The replies of Sentinel carry a raw replication offset for each slave but no lag *time*, as only the `INFO replication` reply of the actual master has that (a `slaveN:...,lag=N` field, being the seconds since the last ACK of that replica). It follows that on each cycle, the same dedicated connection that `RespMetricSampler` already holds is also asked for `INFO replication`, and the per-replica lag that it reports is matched onto the corresponding `RespSentinelStatus` slave row by `ip:port`, populating **`ReplicationLagSeconds`** (null for master and sentinel rows, or if the master could not be reached that cycle). This is the most direct "is a replica falling behind" signal that a Sentinel-monitored Redis deployment offers.
- **`RespSentinelEvent`**: `RespSentinelStatus` above is a once-a-minute poll, which can miss a transition that happens and resolves between two samples, and this table fills that gap. `CacheService` subscribes to every channel on which Sentinel publishes (the `"*"` pattern, covering `+sdown`, `-sdown`, `+odown`, `-odown`, `+switch-master`, `+failover-state`, `+slave`, `+sentinel`, and any future channel type), captures each one the moment it happens into a bounded in-memory queue (mirroring exactly the capture-and-bulk-flush shape of `ApplicationLogEntry`), and `InfrastructureHealthMetricsStarter` bulk-inserts whatever accumulated each minute. Each row is only `OccurredDate`, `Channel` and `Message` (the raw payload of Sentinel for that channel). Every captured event is also logged at Warn, hence it reaches `ApplicationLogEntry` too via the same log4net capture appender, and `RespSentinelEvent` is the structured, Sentinel-specific view of the same information. It is only populated when Sentinel is actually in use.

## etcd and Patroni

Everything above is Postgres or the Resp cache reporting on itself. If a deployment runs Postgres under Patroni (with etcd as the DCS), neither Postgres nor the cache has any concept of that orchestration layer at all, and it follows that the failover decisions of Patroni, and the raft consensus health of etcd, would be a complete blind spot without the sampling described in this section.

### Discovery

`EtcdPatroniDiscovery` finds candidate endpoints for each cluster type, in the order as follows:

1. **An explicit list**: set `EtcdEndpoints` and / or `PatroniEndpoints` to a comma-separated `host:port` list. This is always correct for a real deployment, since guessing topology from hostnames is inherently fragile, and when it is set, the discovery below is skipped entirely for that cluster type.
2. **DNS hostname-prefix probing**, when no explicit list is set: resolution is tried for `"{EtcdDiscoveryPrefix}1"` through `"{EtcdDiscoveryPrefix}{EtcdPatroniDiscoveryMaxNodes}"` (the defaults being the prefix `etcd` and 5 nodes) and likewise for `PatroniDiscoveryPrefix` (default `patroni`), which is the naming convention used by the reference docker-compose demonstration of the Patroni project (`etcd1`, `etcd2`, `etcd3`, `patroni1`, `patroni2`, `patroni3`), and a reasonable default for anyone following it. A plain DNS lookup from inside the container is enough for this to work under Docker Compose, Swarm, or Kubernetes (each resolves service names in this manner), there being no Docker socket and no orchestrator API involved. `EtcdClientPort` (default `2379`) and `PatroniApiPort` (default `8008`) control which port is paired with each resolved hostname.

Discovery is run again on every one-minute cycle rather than being cached, hence a cluster that grows a member is picked up without restarting Jube. A hostname that never resolves is never sampled, and neither table is populated at all when etcd and Patroni are not in use.

### Authentication

The REST API of Patroni is unauthenticated in the deployments that this samples, hence `PatroniMemberStatus` needs no credential for the Patroni hop itself. etcd is different: an etcd cluster with `auth enable` set rejects every v3 call that arrives without a token, including the `cluster/member/list` and `maintenance/status` calls that both samplers make. Upon setting `EtcdClientUsername` and `EtcdClientPassword`, each sampler authenticates once (`POST /v3/auth/authenticate`) and caches the token across all of the endpoints that it polls (the authentication request of etcd is itself replicated through raft, such that a token issued by one member is accepted by every other member), then authenticates again on a `401`, which is what a member that has restarted and lost its in-memory tokens returns. Left unset, the calls go out unauthenticated, which is correct only against an etcd cluster with auth disabled.

It is worth noting what does *not* need a token: `/version`, `/health` and `/metrics` are plain HTTP handlers on the client port rather than v3 RPCs, and answer unauthenticated even with auth on. Because `EtcdMemberStatus` is assembled from a mix of those three handlers and the authenticated v3 RPCs, a wrong or missing credential is a *partial* failure, and an easy one to misread: a sampler that parsed the JSON error body of etcd without first checking the response status would read a refusal as though it were a reply with no fields in it, and still write a row, with `Version`, `ClusterVersion`, `HealthOk` and every Prometheus-derived column correct, with `MemberId`, `LeaderId`, `DbSizeBytes`, `RaftIndex`, `RaftTerm` and `RaftAppliedIndex` all null, and with `AlarmCount` reading `0`, which asserts "no etcd alarms" rather than "alarms unknown".

`EtcdApiResponse.TryRead` therefore gates every v3 response on its status code, and rejects an etcd error envelope (`{"error":..., "code":...}`) even if one arrives with a success status. A rejected call yields no payload rather than an empty one, hence no half-populated row is written at all, and the reason (the message of etcd itself, verbatim, with the endpoint that produced it) is carried on the `LastError` of the sampler and logged by `InfrastructureHealthMetricsStarter` whenever a sampling pass ends up with nothing to write, along with a pointer at `EtcdClientUsername` and `EtcdClientPassword`. The same applies to the `kv/range` read of the DCS history key of Patroni, where an empty result is otherwise indistinguishable from a cluster that has no failover history yet.

Rows already in the table from before that change are still worth reading in the old manner: an `EtcdMemberStatus` row carrying a version but a null `RaftIndex` was a credential problem on the polling service, not an etcd problem. It should be checked per `Instance`, as one service missing the credential looks very much like etcd being half-broken.

The samplers run wherever the engine runs (`EnableEngine=True`), and it follows that every such service needs the credential, not only the one nominally responsible for background jobs.

### `EtcdMemberStatus`

One row per etcd cluster member per one-minute sample, polled directly over the HTTP API of each member (`GET /version`, `GET /health`, `POST /v3/maintenance/status`, `POST /v3/cluster/member/list`, `POST /v3/maintenance/alarm`, `GET /metrics`), where every field name was checked against a live etcd 3.5 instance during development and not taken from documentation alone:

- **Identity**: `Endpoint`, `MemberId`, `Name`, `PeerUrls`, `ClientUrls`, `IsLearner`, `Version`, `ClusterVersion`.
- **Consensus health**: `HealthOk` and `HealthReason`, `LeaderId` (to be compared across the row of every member in the same minute to catch disagreement, a split-brain symptom), `IsLeader` (the id of this member matches `LeaderId`), `HasLeader`, `LeaderChangesTotal`, `RaftIndex`, `RaftTerm` and `RaftAppliedIndex`.
- **Throughput**: `ProposalsCommittedTotal`, `ProposalsAppliedTotal`, `ProposalsPendingCount` and `ProposalsFailedTotal`.
- **Performance**: `WalFsyncAvgMicroseconds` and `BackendCommitAvgMicroseconds` (the cumulative sum and count of etcd itself from `/metrics`, converted to an average, keeping in mind that the guidance of etcd treats sustained values above roughly 10ms as a disk that cannot keep up), `SlowApplyTotal` and `SlowReadIndexesTotal`.
- **Capacity and alarms**: `DbSizeBytes` and `DbSizeInUseBytes`, `AlarmCount` and `Alarms` (a non-zero `AlarmCount`, e.g. `NOSPACE` when the backend quota is exceeded or `CORRUPT` on detected data corruption, means that etcd itself is refusing some operations).

`LeaderChangesTotal` and every `*Total` proposal and slow-operation counter are the cumulative counters of etcd itself (`/metrics` is never reset by Jube), unlike the per-minute event counts of `RespConnectionMultiplexerMetric` above, hence two rows are to be diffed for a rate.

### `PatroniMemberStatus`

One row per Patroni-managed Postgres member per one-minute sample. `GET /cluster` (asked of whichever configured or discovered endpoint answers first) gives the topology of the whole cluster in one call (name, role, state, host and port, timeline and, for replicas, lag already computed by Patroni itself), being the Patroni-native equivalent of the three-call `SENTINEL MASTERS/SLAVES/SENTINELS` of Redis Sentinel. `GET /patroni` is then called once per member for the detail that `/cluster` does not carry:

- **Topology** (from `/cluster`): `Role` (`leader`, `replica` or `standby_leader`), `State`, `Host` and `Port`, `TimelineId`, `LagBytes` (null for the leader, or when Patroni could not compute one).
- **Detail** (from `/patroni`): `PatroniVersion`, `Scope`, `PostgresServerVersion`, `DatabaseSystemIdentifier` (every healthy member should report the same value, and one that does not has diverged), `XlogLocationBytes`, `ReceivedLocationBytes` and `ReplayPaused`, `PendingRestart`, `ClusterUnlocked` (true is a red flag, normally only seen mid-failover).
- **`SyncStandby`**: derived, not reported directly by either endpoint, as the `GET /patroni` response of the leader carries a `replication` array showing the `sync_state` of each connected replica, which is matched onto the row of the corresponding member by name after every endpoint has been sampled that cycle.

Field names for `PatroniMemberStatus` come from the documented REST API of Patroni rather than a live-verified instance (standing up a full Patroni, Postgres and etcd cluster was disproportionate to one sampler), and every read is defensive, such that an unexpected shape degrades to a null column rather than throwing.

### `EtcdClusterEvent` and `PatroniClusterEvent`

`EtcdMemberStatus` and `PatroniMemberStatus` are a once-a-minute poll. To see "what happened" and not only "what is the state right now", each sampler additionally diffs every new sample against the previous one that it took for the same endpoint or member, and emits one row per meaningful change:

- **`EtcdClusterEvent`**: `LeaderChanged` (the view that this member has of who the raft leader is changed, to be compared across members in the same minute to catch disagreement), `HealthChanged` (`GET /health` flipped between ok and not ok), `AlarmRaised` and `AlarmCleared`. This was verified live: activating and clearing a `NOSPACE` alarm against a real etcd instance correctly produced both an `AlarmRaised` and `AlarmCleared` row and a paired `HealthChanged` row (etcd stops serving some requests while an alarm is active, hence the two are genuinely correlated).
- **`PatroniClusterEvent`** (diff-based): `RoleChanged` (leader, replica or standby_leader), `StateChanged`, `TimelineChanged` (a member moved to a new Postgres timeline, typically just after a failover).

Diffing only catches a change that survives from one one-minute sample to the next, and only knows *that* something changed, not *why*. For Patroni there is a better source, as Patroni itself permanently records every failover and switchover (reason, timeline, WAL position, timestamp, and the name of the new leader) in its DCS under a `history` key. Since the REST API of Patroni does not expose that key, **`PatroniClusterEvent`** additionally reads it directly out of etcd (`POST /v3/kv/range`, base64-decoded as per the JSON gateway convention of etcd) whenever etcd is also configured or discoverable, producing `EventType` `Failover` rows with `Reason`, `TimelineId` and `LsnBytes` populated, and with `PreviousValue` and `NewValue` giving the leader that was replaced and the one that took over. This was verified live against a real etcd instance, including confirming that a second read does not emit history entries already seen (tracked in memory by `"{timeline}:{lsn}"`, the natural unique key for one historical transition), and a real bug was caught in the process: the default JSON parser of Json.NET detects ISO-8601-looking strings automatically and silently corrupts them on the way back out as plain strings, hence the history reader parses with `DateParseHandling.None` and does its own explicit, invariant-culture timestamp parsing instead.

Both event tables reset their "has this been seen" state on a Jube restart. The diffs of `EtcdClusterEvent` set a new baseline (a change that happens to straddle a restart is missed, not misreported), while the `history` reader of `PatroniClusterEvent` emits every entry currently in the history of Patroni once more, the same accepted one-time-replay tradeoff that `RespSlowOperation` already makes for the `SLOWLOG` buffer of the Resp server after a restart.

## Docker Monitoring Sidecar (Jube.Monitoring)

Everything above is sampled without leaving the Jube process and the connections that it holds. Docker host and container metrics are the one exception: reading them properly needs the Docker Engine API, which needs the Docker socket (`/var/run/docker.sock`) mounted into whichever container reads it, and Jube.App must never hold that mount, since it is a much larger blast radius than the narrow, host-local visibility that this is meant to provide. `Jube.Monitoring` exists to resolve that: a small, standalone process and image (never a module inside Jube.App or Jube.Engine), deployed one instance per Docker host, which alone holds the socket and uses it in two ways as follows:

- It samples `ContainerLogEntry`, `HAProxyServerStatus`, `HAProxyReachabilityProbe` and `OverlayNetworkTaskDrift` on its own loop and writes them straight into the same shared Postgres database that Jube itself uses.
- It answers `GET /proxy?path=...` with the response of the Docker Engine API for a short allow-list of read-only paths (`/containers/json`, `/containers/{id}/stats`, `/containers/{id}/json`, `/info`, `/version`, `/system/df` and `/events`), any other path being refused with 403, alongside a `GET /health` probe. `InfrastructureHealthMetricsStarter` samples `DockerContainerMetric`, `DockerHostMetric` and `DockerEvent` through that proxy, and only when the `DockerMonitoringProxyUrl` Environment Variable of Jube.App is set (it has no default, and the three sampling groups are skipped when it is unset), which is to say Jube.App reads Docker through the sidecar and never through the socket.

It shares the `Poco`, `DbContext` and `Repository` classes of `Jube.Data` with the rest of the system rather than defining its own copies, specifically to avoid the class of bug that comes of two independently maintained schemas, the one real cost being that the transitive dependencies of `Jube.Data` are pulled in (the analytics libraries included), which only grows the disk footprint of the image since the .NET runtime never loads an assembly into which it does not call. It has no dependency on `DynamicEnvironment` or log4net: configuration is read directly from environment variables, being `ConnectionString` (required); `DockerSocketPath`, defaulting to `/var/run/docker.sock`; `SampleIntervalSeconds`, defaulting to `60`; `HAProxyStatsUrl`, defaulting to `http://haproxy:7000/;csv`; and `HAProxyTasksHostname`, defaulting to `tasks.haproxy` (the latter two being described below), together with the optional `EnableOpenTelemetry` and `OpenTelemetryBackendEndpoint` for exporting the meter of the sidecar itself, and `SecretsPath` for substituting secrets into the connection string. It talks to the Docker Engine API over a Unix domain socket `HttpClient` (the same `SocketsHttpHandler.ConnectCallback` pattern that Docker.DotNet uses internally) rather than any client SDK, consistent with how this suite calls the HTTP APIs of etcd and Patroni directly, as above. A failed sample or write is logged to the console and retried on the next cycle.

### `DockerContainerMetric`

A narrow table, having one row per container per one-minute sample and filtered by `OccurredDate`, covering every container on the host, in any state:

- **Identity and state**: `ContainerId`, `Name`, `Image`, `State`, `Status` (the strings of Docker itself), `HealthStatus` (the Docker `HEALTHCHECK` status, or `none` when the image defines none).
- **Lifecycle**: `RestartCount`, `OomKilled`, `ExitCode`, `StartedAt`, all of which are only available via the container-inspect endpoint of Docker, not the container list or stats endpoints.
- **CPU and memory**: `CpuUsagePercent` (computed in the same manner as `docker stats` computes it, as the non-streaming stats reply of Docker already carries both the current and previous sample in one call, hence no state needs to be kept across polling cycles), `OnlineCpus`, `MemoryUsageBytes`, `MemoryLimitBytes` and `MemoryPercent` (raw usage including reclaimable page cache, hence this reads a little higher than the cache-adjusted figure of `docker stats`).
- **Network and block I/O**: `NetworkRxBytes` and `NetworkTxBytes` (summed across every network interface that the container has), `BlockReadBytes` and `BlockWriteBytes` (summed from cgroup block-io accounting).
- **Process count**: `PidsCurrent` and `PidsLimit`.

### `DockerHostMetric`

A wide table, having one row per host per one-minute sample and filtered by `CreatedDate` (there is no `OccurredDate` on this one, the same convention that `PostgresMetric` and `RespMetric` use):

- **Counts**: `ContainersTotal`, `ContainersRunning`, `ContainersPaused` and `ContainersStopped`, `ImagesCount`.
- **Host identity**: `NCpu`, `MemTotalBytes`, `DockerVersion`, `ApiVersion`, `KernelVersion`, `OperatingSystem`, `OsType`, `Architecture`.
- **Disk usage**, from `GET /system/df` (which carries no pre-aggregated totals of its own, every one of these being a manual sum over the arrays of that endpoint): `LayersSizeBytes`, `ImagesSizeBytes`, `ReclaimableImagesBytes` (images referenced by zero containers, being candidates for `docker image prune`), `ContainersDiskBytes` (the sum of the writable layer of every container), `VolumesSizeBytes` (the sum of every volume that has computed usage data), `BuildCacheSizeBytes`.

### `ContainerLogEntry`

The other side of "never need to log into the box": the stdout and stderr of every container on the host, with no name filtering, captured via `GET /containers/{id}/logs`, the same Docker Engine API endpoint that `docker logs` itself calls, over the socket that `Jube.Monitoring` holds. This is what actually closes the gap for etcd, Patroni and the Resp server (Garnet, or Redis and Sentinel): none of them expose their own process logs over any API or wire protocol of their own, but the log stream of Docker is available for every one of them regardless, since Docker itself is what is actually holding onto that output.

- **Every container, deliberately unfiltered**: the same "every container, no exceptions" choice that `DockerContainerMetric` already makes, such that there is no per-system name list to keep synchronised with whatever a given deployment actually runs. It does follow that the console output of the containers of Jube itself lands here too, alongside (not instead of) the log4net-sourced capture of `ApplicationLogEntry`, being a genuinely different source (raw stdout as against structured log4net events, useful for example for a crash before log4net itself has initialised) rather than a duplicate worth filtering out.
- **Incremental, not read again each cycle**: the `logs` endpoint of Docker accepts a `since` parameter (a UNIX timestamp, with nanosecond precision as `seconds.nanoseconds`), the last-ingested-line timestamp of each container is tracked in memory (per Docker container id, not name, as a recreated container is given a new id and correctly starts fresh) and the next poll asks for `since = last + 1ns`. It was confirmed live against a real Docker Engine that `since` is *inclusive*, the exact boundary nanosecond being returned again on a repeat request, hence the `+1ns` is required and is not merely defensive. On the *first* cycle in which a given container id is seen, the cursor starts at "now" rather than backfilling the entire retained log history of that container.
- **Multiplexed stream demuxing**: when a container is not running with a TTY (true for every container that this targets), Docker interleaves stdout and stderr in one byte stream framed as 8-byte headers (`[stream_type, 0, 0, 0, big-endian uint32 length]`) followed by exactly that many payload bytes. `DockerApiClient.GetContainerLogsAsync` demuxes this into separate stdout and stderr byte buffers (concatenated before UTF-8 decoding, since both a log line and a multi-byte UTF-8 character can straddle two frames) before splitting into individual lines, all of which was confirmed by inspecting raw response bytes against a real Docker Engine and not taken from documentation alone.
- **Timestamp parsing**: every line carries the RFC3339Nano prefix of Docker (`timestamps=true` is always requested), parsed into `OccurredDate` and stripped from `Message`, whereas a line that does not match the expected 30-character prefix shape falls back to storing the whole line as `Message` with no `OccurredDate`, rather than being dropped.
- **Purged, not permanent**: included in the same weekly purge cycle as every other table in this suite (unlike `UserLogin` and `UserLogout`, which are permanent audit trails and deliberately excluded from purging, as set out in the Purging section below).

### `DockerEvent`

This table fills the gap that the once-a-minute snapshot of `DockerContainerMetric` leaves: a container that was OOM-killed and restarted between two polls shows up there only as an incremented `RestartCount`, with no record of exactly when or why. `GET /events` (the same Docker Engine API endpoint that `docker events` itself calls) carries that as a discrete, timestamped fact instead: container start, stop, die, kill, oom and health_status, network connect and disconnect, volume mount and unmount, image pulls, and (in Swarm scope) service, node, secret and config events too. It makes the same "every container, no filtering" choice as `ContainerLogEntry`, being one host-wide event timeline, not scoped to any particular container name.

- **`EventType`, `Action`, `ActorId`, `ActorName`, `Scope`**: taken directly from the event JSON of Docker (`Type`, `Action`, `Actor.ID`, `Actor.Attributes.name`, `scope`). `Scope` is `local` or `swarm`.
- **Incremental, by the same mechanism as `ContainerLogEntry`**: `GET /events` accepts `since` and `until` (both required here, since omitting `until` switches the endpoint into a long-poll, streaming mode that a once-a-cycle polling model cannot use). It was confirmed live that `since` is inclusive at nanosecond precision in the same manner as the logs endpoint, hence the next poll asks for `since = last + 1ns`, `until = now`. There is one shared cursor, not one per container, as `/events` is a single host-wide timeline covering every actor (container, network, volume, image and so on), unlike the per-container log streams of `ContainerLogEntry`. It starts at "now" on the first cycle, with no backfill.
- **`docker exec` audit trail, and a caveat that comes with it**: `exec_create`, `exec_start` and `exec_die` events fire whenever anyone runs `docker exec` against a container, and the `Action` string of Docker for `exec_create` and `exec_start` embeds the *exact command line* verbatim (confirmed live: `"exec_create: psql -U postgres -c ..."`). This is a genuine audit signal, answering whether anyone bypassed the application and touched a container directly, and with what command, but it cuts both ways: a command line containing a secret as a bare argument (e.g. `psql -c "ALTER USER x PASSWORD 'y'"`) would be captured here too, in plain text, queryable by anyone who can browse this table (the landlord). This is an existing property of the Docker Engine API itself, not something that this table introduces or could reasonably filter out (there is no reliable way to distinguish "a command line with a secret in it" from any other command line), and it should be treated in the same manner as shell history on the host itself.
- **Purged, not permanent**: the same weekly cycle as `ContainerLogEntry`, for the same reason (this is operational visibility, not the `UserLogin` and `UserLogout` audit trails).

### `HAProxyServerStatus`

Everything above monitors the process of Jube itself or the Docker host underneath it, and nothing watches HAProxy, even though every request to `jube-ui` and `jube-api`, and every Postgres connection, passes through it first. `HAProxyServerStatus` closes that gap by scraping the stats CSV of HAProxy (`http://haproxy:7000/;csv` by default, being the `HAProxyStatsUrl` environment variable, matching the `haproxy.cfg` of the reference topology, which uses `stats uri /` and not `/stats` as some HAProxy documentation examples assume) once per sample cycle, writing one row per individual server slot. The `FRONTEND` and `BACKEND` aggregate rows are skipped, since a single dead slot is the signal that this table exists to catch, not the backend-wide totals.

- **Identity and health**: `PxName` and `SvName` (the proxy and server-slot names, e.g. `jube_ui` and `jube-ui-3`), `Status` (`UP`, `DOWN`, `MAINT` and so on), `Addr` (the IP:port that HAProxy currently has resolved for that slot, being the field that proves or disproves "HAProxy thinks a slot is live at an address on which nothing is listening any longer"), `CheckStatus` and `CheckCode` (the result and HTTP status of the last health check).
- **Flapping and load**: `ChkFail` and `ChkDown` (cumulative failed checks and down-transitions), `LastChg` (seconds since the status of this slot last changed, where a slot cycling status every few seconds shows a small, unstable `LastChg` rather than one clean failure), `Scur` and `Qcur` (current sessions and queued requests), `Weight`, `Act` and `Bck`. `Hrsp2Xx` and `Hrsp5Xx` are populated for `jube_ui` and `jube_api` (HTTP mode) and left null for `postgres_primary` and `postgres_replicas` (TCP mode).
- **Field lookup by CSV header name, not positional index**: the stats CSV of HAProxy has grown new trailing columns across versions, hence `HAProxyServerStatusSampler` parses the header row into a name-to-index map rather than hardcoding column positions, and it keeps working across an HAProxy upgrade that adds columns.

### `HAProxyReachabilityProbe`

`HAProxyServerStatus` above is the view that HAProxy has of its own backends, whereas this table is the view from the client, which is to say synthetic checks against HAProxy from the outside, the one thing that `/api/ready` structurally cannot see, since that endpoint only proves that a container can answer on its own loopback. Every sample cycle, `Jube.Monitoring` resolves `tasks.haproxy` by default (the `HAProxyTasksHostname` environment variable, following the per-task DNS convention of Swarm, which returns the address of every individual HAProxy replica directly rather than the VIP and IPVS-balanced address of the `haproxy` hostname) and probes each replica on its own:

- **`JubeUi` / `JubeApi`**: a real `GET /api/ready` issued straight at the `5001` or `5002` port of that replica, exercising the same routed path that a genuine client request takes. `HttpStatusCode` and `ConnectMicroseconds` (from the start of the connection attempt to success or failure) are recorded either way.
- **`PostgresPrimary` / `PostgresReplica`**: a bare TCP connect to the `5432` or `5433` port of that replica, as a full login would need credentials that this sidecar has no reason to hold beyond what it already uses for its own writes.
- **Per-replica attribution**: resolving `tasks.haproxy` instead of `haproxy` means that a problem specific to the HAProxy of one node (or the overlay path to it) shows up as "this one replica fails, the others do not" in `HAProxyAddress`, rather than being averaged away by the load balancing of the VIP across a shared hostname.
- **`Success` / `ErrorMessage`**: `ErrorMessage` (the exception message, truncated to 1024 characters) is populated only on failure, and a TCP connect that times out after 5 seconds is treated as a failure like any other.

### `OverlayNetworkTaskDrift`

This is the one signal genuinely new to this whole suite: whether the embedded DNS of Docker agrees with what the scheduler of Swarm actually has running. The `server-template` directive of HAProxy (and anything else relying on DNS to discover the current tasks of a service) depends entirely on that agreement holding, and a stale DNS answer pointing at a task that was already rescheduled is exactly the overlay-network and DNS desynchronisation class of bug that this table exists to catch, independently of whether any health check has caught up to it yet.

- **Manager-only**: the Swarm Tasks API is only answerable from the Docker socket of a manager node, hence each `Jube.Monitoring` instance checks `Swarm.ControlAvailable` via `GET /info` first and produces no rows at all when running on a worker node, rather than reporting a false "no tasks" drift.
- **Always `tasks.<ServiceName>`, never the plain service name, for every service checked**: `jube-ui` and `jube-api` (`dnsrr` mode) happen to resolve in the same manner whichever form is asked, but every other service that the sampler checks (`haproxy`, `patroni1` to `patroni4`, `garnet1` to `garnet4`, `redis-master` and `redis-replica1` to `redis-replica3`, `sentinel1` to `sentinel5`, `etcd1` to `etcd5`, such that both the Garnet and the Redis variant of the reference topology are covered) uses the default VIP endpoint mode, where the plain service name resolves to a virtual IP that IPVS transparently redirects, never the real overlay address of the task. Comparing a VIP against the real task addresses of the Swarm API would report every such service as permanently "inconsistent" and defeat the point, whereas `tasks.<ServiceName>` bypasses the VIP uniformly for every service, VIP-mode or not, such that the comparison is meaningful across the board.
- **`DnsResolvedAddresses`, `SwarmTaskAddresses`, `AddressesOnlyInDns`, `AddressesOnlyInSwarm`**: the two full address sets (comma-joined) and their two one-sided differences. A non-empty `AddressesOnlyInDns` is a stale DNS answer for a task that no longer exists, and a non-empty `AddressesOnlyInSwarm` is a newly scheduled task to which DNS has not caught up yet. `IsConsistent` is `true` only when both differences are empty, being the headline column for spotting drift at a glance.

### Deployment

One `Jube.Monitoring` instance is needed per Docker host, each with the socket of that host mounted, as a single instance can only ever see the daemon to which it is socket-mounted, and it follows that a multi-host deployment needs one per host and not one shared instance. The root `docker-compose.yml` includes a `jube-monitoring` service for the single-host case, with `DockerMonitoringProxyUrl=http://jube-monitoring:8081` set on Jube.App, while `Jube.Cluster/docker-compose.yml` (the Swarm reference topology) deploys it with `mode: global` such that every node, manager or worker, runs its own instance reporting on its own local Docker daemon.

## Dedicated diagnostic connections

The Postgres and Resp *server* samples (`PostgresMetric`, `RespMetric`, `RespSlowOperation`) are taken over connections dedicated to this purpose, entirely separate from the pooled connections of the application itself (the connection pool of `Jube.Data`, and the multiplexer of `Jube.Cache.CacheService`). This is deliberate: diagnostics need to keep working even when the connections of the application are the thing in trouble, which is exactly the kind of incident that these tables exist to help diagnose. The Resp diagnostic connection additionally sets `AllowAdmin`, since `INFO` and `SLOWLOG` are admin-only commands in the StackExchange.Redis client and the production connection of the application deliberately does not set that flag. `RespConnectionMultiplexerMetric` is the deliberate exception, as it samples the connection of the application *itself* precisely because the health of that connection is the thing being measured.

## Postgres's own server log (`PostgresLogEntry`)

The other half of "never need to log into the box" is the server log of Postgres itself, which is to say checkpoints, connection issues, deadlocks, crashes, slow autovacuum, and everything else that Postgres writes about its own operation, tailed over plain SQL with no filesystem or Docker socket access needed. `pg_ls_logdir()` finds the current log file (name, size, modification time) and `pg_read_file(path, offset, length)` reads exactly the bytes written since the last cycle, both being confirmed live against a real Postgres instance to return genuine log content, including real `LOG`, `ERROR` and `STATEMENT` lines.

- **Prerequisite, `logging_collector = on`**: this is off by default in vanilla Postgres. When off, `PostgresLogSampler` reports `LoggingCollectorOff` and the flush cycle skips cleanly (one WARN being logged the first time, never repeated) rather than treating it as an error, and the table stays empty until the setting is turned on and Postgres is restarted (`logging_collector` is not reloadable). The connecting role also needs `pg_read_server_files` or superuser, the same privilege level that every other sampler in this suite already assumes.
- **Incremental tailing, not read again each cycle**: the first cycle after starting records the *current* end of the current log file as its starting offset rather than replaying whatever history is already in it (a Postgres log file has no bound on how large that history could be, unlike the small JSON history array of Patroni, which this suite *does* fully replay once, as set out under `PatroniClusterEvent` above). Every subsequent cycle reads only the delta since the last one. Rotation onto a new filename resets the tracked offset to zero for the new file (any final unread bytes of the old file are acceptably lost, the same best-effort tradeoff that this whole suite makes elsewhere), and the same filename shrinking below the tracked offset (a fixed-name rotation scheme reusing a name from scratch) does the same.
- **Line parsing**: the default `log_line_prefix` of Postgres (`%m [%p] `) gives `<timestamp with ms and timezone name> [<pid>] <LEVEL>:  <message>`, and each line matching that shape becomes one row (`OccurredDate`, `Pid`, `Level`, `Message`). A deployment running a different `log_line_prefix` does not break this, as lines that do not match become their own `Level = null` entry rather than being dropped or crashing the sampler. Continuation-style lines that Postgres sometimes emits with their own full prefix (a `STATEMENT`, `DETAIL`, `CONTEXT` or `HINT` line following an error) become their own rows too, each correctly tagged with its own `Level` and `Pid`, it having been confirmed live that Postgres gives these their own complete prefix rather than emitting them bare.
- **No `Exception` column**, unlike `ApplicationLogEntry`: the log format of Postgres has no separate split between exception and message, and a `STATEMENT`, `DETAIL` or `CONTEXT` line that *does not* carry its own prefix (some Postgres versions and configurations do run continuation lines together) is folded into the `Message` of the previous entry, newline-separated, rather than a placeholder.
- **Purged, not permanent**: included in the same weekly purge cycle as every other table in this suite (unlike `UserLogin` and `UserLogout`, which are permanent audit trails and deliberately excluded from purging, as set out in the Purging section below).
- It is browsable via `GET /api/PostgresLogEntry` and the Postgres log area of the Performance page under Administration, with the same conventions as every other table here (`take`, `from`, `to`, `search` against `Message` or `Level`, `samplePercentage`, and CSV export).

This complements, rather than duplicates, `PostgresMetric` and `PostgresReplicationStatus` above: those are the numeric self-view of Postgres (`pg_stat_*`), whereas this is its own narrative account of what happened and when, in the words of Postgres itself.

## Live activity and blocking (`GET /api/PostgresActivity`)

This is deliberately not shaped like anything else in this suite, being neither a per-minute snapshot, nor stored, nor purged. `pg_stat_activity`, which is to say every backend about which Postgres currently knows, from ordinary application connections to its own autovacuum, checkpointer and background-writer workers, reflects the instant at which it is queried, hence a row from a minute ago says nothing about a lock that formed and cleared thirty seconds later. The Postgres activity area of the Performance page under Administration queries it live on demand via Refresh, in the manner that a DBA actually uses this view, rather than trying to force it into the once-a-minute historical shape that everything else here uses. Refresh is manual rather than timer-driven so that the grid never sorts itself again from under someone reading it.

- **Real blocking-chain detection, confirmed live**: `pg_blocking_pids(pid)`, a built-in PostgreSQL function requiring no extension, resolves the actual "who is blocking whom" answer, not merely "this backend is waiting on something". It was verified against a real lock conflict (one session holding a row lock, a second blocked behind it), where the `BlockedByPids` of the blocked backend correctly named the exact PID holding the lock, with the real query text and wait state of both backends visible.
- **Zero extra configuration**: no `logging_collector`, no `shared_preload_libraries`, no restart. It works against a stock Postgres install.
- **A dedicated connection, deliberately**: `PostgresActivityRepository` opens its own connection, separate from the pooled application connection against which the permission check of this page runs, for the same reason that `PostgresMetricSampler` and `PostgresLogSampler` do: this is precisely the tool reached for when something about the database is already wrong, which is exactly when the connection pool of the application is most likely to be part of the problem.
- **Read-only by design**: it surfaces everything needed to identify a stuck query or a connection-leak pattern (`state = 'idle in transaction'` held for a long time is the classic signature), but does not offer `pg_cancel_backend` or `pg_terminate_backend` from the page itself. `PostgresActivityDto.Pid` is exactly what an operator would pass to either function directly in `psql` if a kill is actually warranted.
- **The complement to this page is `PostgresStatementStatistics` below**: this page answers "what is running right now", whereas that one answers "which query *shape* is worst overall, across all history".
- It is not tenant-scoped (this is server-wide activity, not the data of Jube itself) and is restricted to the landlord tenant like every other infrastructure viewer in this suite.

## Per-query aggregate statistics (`GET /api/PostgresStatementStatistics`)

This is `pg_stat_statements`, which is to say aggregate statistics per *query shape*: calls, total, mean, min, max and stddev execution time, rows, cache-hit as against disk-read bytes, temp-file spill bytes and WAL bytes, accumulated across all history since the extension was created or last reset, and not only for currently running backends. Unlike `PostgresActivity` above, this genuinely is a running total and not an instant-in-time view, hence a query shape that ran once, five minutes ago, still shows up here with its numbers intact. The Postgres statement statistics area of the Performance page under Administration queries it live on demand via Refresh, with the same manual-refresh convention as `PostgresActivity`, and sorts worst total time first by default.

- **Requires deployment-level setup, unlike everything else in this suite**: `shared_preload_libraries = 'pg_stat_statements'` must be set server-side, followed by a restart, because the extension needs a shared-memory hook registered at postmaster start, and `CREATE EXTENSION` alone does not fail without it, leaving instead a dead extension that only errors the first time something queries the view. `AddImplicitAsyncRecallAndTimeoutFeatures`, the migration that creates this extension, guards against exactly this: its first statement checks that `vector`, `pg_trgm` and `pg_stat_statements` are actually available on the server and that `pg_stat_statements` is actually preloaded, and raises one clear error covering all of it before any other DDL in that migration runs, rather than a half-applied migration or a confusing runtime failure here later. `Jube.Cluster/PgStatStatementsRollout.md` sets out the actual rollout steps against an already-running cluster.
- **A dedicated connection, deliberately**: `PostgresStatementStatisticsRepository` opens its own connection, by the same reasoning as `PostgresActivityRepository` above.
- **Read-only by design**: it does not expose `pg_stat_statements_reset()` from the page itself, matching the choice of `PostgresActivity` not to offer `pg_cancel_backend` or `pg_terminate_backend`.
- It is not tenant-scoped and is restricted to the landlord tenant like every other read-only infrastructure viewer here.

## Sampling architecture: fan-out, join and OpenTelemetry

`InfrastructureHealthMetricsStarter` runs twenty-one independent sampling groups concurrently each minute (via `Task.WhenAll`), rather than one after another. With as many samplers as this starter now carries (the .NET runtime, Postgres, the server log of Postgres, the Resp server, the live Resp connection multiplexer, the Resp Sentinel and connection event drains, the per-minute Resp call counters, etcd, Patroni, and its own OpenTelemetry metric capture), a single slow or unreachable dependency would otherwise stall every sampler behind it in a serial chain for the rest of the minute. In practice this matters most for etcd and Patroni: when neither is configured or discoverable, each DNS-based discovery probe still has to time out for every candidate hostname before giving up, and running that concurrently with the always-fast Postgres, Resp and runtime samples keeps the cycle of one minute bounded by the *slowest* sampler rather than the *sum* of all of them.

Each group opens its own dedicated `DbContext` (one Npgsql connection each), which is necessary because a single ADO.NET connection, and the LinqToDB `DataConnection` wrapping it, cannot run concurrent commands from more than one caller. Eleven of the groups write the tables of this page that are sampled from inside the engine, and are numbered for the purposes of the explanation that follows:

1. `DotNetRuntimeMetric`
2. `PostgresMetric` + `PostgresReplicationStatus`
3. `RespMetric` + `RespSlowOperation` + `RespSentinelStatus`
4. `RespConnectionMultiplexerMetric`
5. `RespConnectionEvent`
6. `RespSentinelEvent`
7. `RespCallCounter`
8. `EtcdMemberStatus`
9. `PatroniMemberStatus`
10. `OpenTelemetryMetric`
11. `PostgresLogEntry`

The remaining ten groups, each also running in parallel on its own `DbContext`, are the three Docker groups read through the proxy of the sidecar (`DockerContainerMetric`, `DockerHostMetric` and `DockerEvent`, skipped when `DockerMonitoringProxyUrl` is unset), and seven flushes of counters and capture queues that belong to other pages (`HttpProcessingCounter`, the asynchronous queue balance, `ModelInvokeWarning`, `CaseCreationStagePerformanceCounter`, `CaseCreationWarning`, `ArchiverWarning` and `CaptureQueueHealth`, for which see [Background Processing Performance](../BackgroundProcessingPerformance/index.html)).

Groups 2 and 3 bundle more than one sample because `PostgresMetricSampler` and `RespMetricSampler` each hold one long-lived connection plus delta and dedup state (`lastSample`, `lastSeenSlowLogId` and so on) across their own methods that is not safe to call concurrently with itself, hence those samples stay sequential *within* their group, while the group as a whole still runs in parallel with every other group. Every other sampler here is either stateless or keeps its mutable state scoped to the sequential call chain of one group, hence no locking is needed between groups, and `EtcdPatroniDiscovery`, used by both groups 8 and 9, is itself a stateless helper (constants only, no instance fields), such that calling it concurrently from two different groups is safe. Group 7, `RespCallCounter`, is the same read-and-reset shape as the per-model Task, Stage and Response Time Pipeline counters of `ManageCountersStarter`, only global rather than per-model, in that it drains `Jube.Cache.Observability.CacheCallCounters`, the dedicated accumulator that the `CacheDiagnostics.Record` call of every Jube.Cache repository method also feeds, rather than polling an external dependency. Group 10 is a different shape again, as it does not poll an external dependency at all either, but drains an in-process aggregation of the OpenTelemetry metrics of this same process (see [Local capture of Jube's own OpenTelemetry metrics](#local-capture-of-jubes-own-opentelemetry-metrics) below). Group 11, `PostgresLogEntry`, holds its own dedicated connection in the same manner as `PostgresMetricSampler` and for the same reason, but tails the server log of Postgres rather than the `pg_stat_*` views, as set out in the dedicated section above.

Every sampling operation is given its own OpenTelemetry span and metric regardless of the group inside which it runs, via `Jube.Engine.Observability.SamplerScope` (which mirrors the span-plus-counter-plus-histogram shape of `Jube.Service.Observability.OperationScope`, minus the actor, tenant, audit and change-event concerns that only make sense for a user-initiated service call). Each span nests under one parent `InfrastructureHealthMetrics.Cycle` activity for the minute, tagged `jube.sampler`, `jube.outcome` (`ok`, `skipped` or `error`) and `jube.row.count`, while `EngineDiagnostics.SamplerCount` and `EngineDiagnostics.SamplerDuration` (`jube.engine.sampler.count` and `jube.engine.sampler.duration`, tagged `sampler` and `outcome`) carry the same information as exported metrics. Both are emitted through the existing `ActivitySource` and `Meter` of `Jube.Engine` (`EngineDiagnostics`), which the `AddOpenTelemetry` of `Jube.App/Startup.cs` already registers for both tracing and metrics export whenever `EnableOpenTelemetry` is on, and `jube.engine.sampler.*` are themselves, in turn, exactly the kind of measurement that group 10 captures locally.

## Local capture of Jube's own OpenTelemetry metrics

Everything that `ServiceDiagnostics` and `EngineDiagnostics` record (`jube.service.operation.*`, `jube.engine.stage.duration`, `jube.engine.sampler.*`, `jube.engine.logs.warn.count`) is, by default, only visible via the OTLP exporter, which is to say only if a deployment has an external OpenTelemetry collector configured at all. `OpenTelemetryMetricCapture` gives every deployment a local, queryable copy of the same data, by attaching a second, independent `MeterListener` alongside whichever one the OpenTelemetry SDK itself may already be running (it was confirmed live that multiple `MeterListener` instances can observe the same `Meter` concurrently with no interference). It is started unconditionally from `Startup.cs`, before the application begins accepting requests, and runs regardless of whether `EnableOpenTelemetry` or an external collector is configured.

This deliberately does not store one row per raw measurement. A histogram like `jube.engine.stage.duration` is recorded up to seventeen times on every single invocation, and capturing every raw measurement would reintroduce exactly the per-transaction volume problem that OpenTelemetry metrics exist to avoid on the hottest path of this codebase (see [Sampling architecture](#sampling-architecture-fan-out-join-and-opentelemetry) above, and the wider discussion of `/api/invoke` telemetry upon which this suite is built). Instead, measurements are aggregated in-process into one Count, Sum, Min and Max bucket per distinct (`MetricName`, `Tags`) combination, bounded by cardinality (stages by models, areas by outcomes and so on) and not by transaction volume, and only the aggregate is written out, once a minute, by group 10 above. This mirrors what the OTLP exporter itself already does internally before handing data to a collector, the difference being that the destination is a local Postgres table as well as (or instead of) an external backend.

- **`OpenTelemetryMetric`**: one row per distinct (`MetricName`, `Tags`) combination per one-minute drain, with `MetricName` (the OpenTelemetry instrument name), `InstrumentType` (`Counter`, `Histogram` and so on), `Tags` (a sorted `key=value,key=value` string), `Count`, `Sum`, `Min` and `Max` for that window. It is browsable via `GET /api/OpenTelemetryMetric`, with the same conventions as every other table in this suite (landlord-only, not tenant-scoped, `take`, `from`, `to`, `search` and `samplePercentage`, with `search` matching `MetricName` or `Tags`).

Two pages that an administrator can edit sit alongside this local capture: [OpenTelemetry Log Counter](../OpenTelemetryLogCounter/index.html) turns a regex match against any of the unstructured log sources of this page into a new counter without a code change, and [OpenTelemetry Exclude](../OpenTelemetryExclude/index.html) stops a named instrument, be it one of those or any other, from being exported at all. A third, [OTLP Dispatch Counter](../OtlpDispatchCounter/index.html), reports on the export pipeline itself once `EnableOpenTelemetry` is on: dispatch success and failure, response times, and drops caused by a full export queue.

### Sampling the listener itself

`OpenTelemetryMetricCaptureSamplePercentage` (default `100`, which is to say every measurement, being the original behaviour of this suite and unchanged unless explicitly configured) controls what fraction of raw measurements the capture `MeterListener` even looks at, before any aggregation happens. This answers a different question from the read-side `samplePercentage` that the `GetLastAsync` of every table already takes: that one thins out which already-aggregated *rows* a caller sees when browsing, whereas this one thins out which raw *measurements* are counted in the first place, trading accuracy for CPU cost on whatever hot path is emitting them.

This exists because the meter list has grown well beyond the once-a-minute InfrastructureHealthMetrics samplers that it started out covering, in that `Microsoft.AspNetCore.Hosting`, Kestrel, `Microsoft.AspNetCore.Authentication`, `Microsoft.AspNetCore.Authorization`, and outbound `System.Net.Http` calls all fire on *every single HTTP request*, not once a minute. The sample check runs as the very first thing in the callback of the listener, before the per-measurement work of turning the tag list into a string key and before the aggregator dictionary lock, hence it sheds real CPU cost proportionally rather than merely producing fewer output rows (row count was already bounded by cardinality, not traffic, and so was never the concern).

Below 100, the `Count` and `Sum` of every aggregate become an estimate scaled down by roughly that fraction, not the true total, while `Min` and `Max` remain the minimum and maximum of whatever was actually sampled, which converges towards the true values as volume increases but is not guaranteed to equal them. How many measurements were skipped in this manner (`OpenTelemetryMetricCapture.SampledOutCount`) and how many distinct series were dropped for exceeding the defensive cardinality cap (`DroppedNewSeriesCount`) are both tagged onto the `OpenTelemetryMetric` sampler span every flush cycle, regardless of whether that cycle had anything new to write out.

### Beyond Jube's own meters -- host, process and framework telemetry

`OpenTelemetryMetricCapture.Start(...)` also listens to a handful of meters that this application does not own, such that the same `OpenTelemetryMetric` table captures them too, rather than that data only ever reaching an external OTLP collector:

- **`System.Runtime`**: the built-in native meter of .NET (present since .NET 8/9 regardless of any OpenTelemetry package): host process CPU time (`dotnet.process.cpu.time`), GC generations, pause time and heap size, JIT compilation time, thread pool thread and queue counts, assembly count, lock contentions.
- **`System.Net.Http`**: native outbound HttpClient request duration and count.
- **`Microsoft.AspNetCore.Hosting`** / **`Microsoft.AspNetCore.Server.Kestrel`**: native inbound request duration and count, and Kestrel connection and queue metrics (`/api/invoke` itself is excluded from the *tracing* side of ASP.NET Core instrumentation for volume reasons, but these aggregate metrics carry no per-transaction cardinality, hence they are not excluded here).
- **`OpenTelemetry.Instrumentation.Process`**: process memory (working set and virtual) and CPU time under the semantic-convention names of OpenTelemetry (`process.memory.usage`, `process.memory.virtual`, `process.cpu.time`, `process.uptime`). This one Meter is only ever created once `AddOpenTelemetry` actually builds its `MeterProvider`, hence unlike the four native meters above it is only populated when `EnableOpenTelemetry` is on.

The first three are genuinely free, as .NET does not compute these instruments at all until something starts listening (confirmed live), and it follows that registering them here is what turns them on, such that they are captured locally even with `EnableOpenTelemetry` off and no OpenTelemetry packages wired at all. There is no separate "host" metrics package in the .NET OpenTelemetry ecosystem beyond this (checked, none exists), and container-level CPU and memory *limits and throttling* are instead covered by the `Container*` columns of `DotNetRuntimeMetric`, read directly from cgroup (see above).

## Aspire-parity tracing additions

Two small, deliberate additions were made to the `/api/invoke` hot path itself alongside the metrics work above, matching what a .NET Aspire-orchestrated service would give by default:

- **Redis**: `AddRedisInstrumentation` (the instrumentation package of the StackExchange.Redis client, which serves Garnet and Redis alike) is wired against both `CacheService.ConnectionMultiplexer` (the connection that `TtlCounterExtensions` and `CacheWalRepository` use during a normal invocation) and `CacheService.SentinelMultiplexer` (when Sentinel is in use). This puts a handful of Resp command spans on the hot path, which is a materially smaller addition than a whole-invocation span, and one for which the earlier "no tracing on /api/invoke" stance of this suite was explicitly relaxed. The spans are harvested from the profiling API of StackExchange.Redis on a timer (`StackExchangeRedisInstrumentationOptions.FlushInterval`, default 10 seconds) rather than emitted synchronously per command, hence there is no per-command latency cost on the hot path, only a bounded delay before the span becomes visible and exported.
- **RabbitMQ**: `RabbitMQ.Client` 6.2.1 (the version that this repository pins) predates the built-in tracing of that library (added around 6.6), and there is no widely used contrib instrumentation package for it. The one RabbitMQ touch point on the invoke hot path (`PublishToAmqp`, conditional on `AMQP` being enabled) is instrumented by hand instead, via `EngineDiagnostics.ActivitySource`, tagged with the standard messaging semantic conventions plus `jube.entity_analysis_model_instance_entry_guid`, keeping in mind that a span attribute carries no cardinality cost in the manner that a metric tag would, hence this is exactly where "trace back to the transaction guid" belongs.

Npgsql is the one dependency for which spans are not produced. The version of Npgsql in use carries a native `ActivitySource`, but the tracing registration in `Jube.App/Startup.cs` adds only the Service and Engine sources, ASP.NET Core, HttpClient and the Resp multiplexers, hence no Postgres command spans are produced, and Postgres client telemetry is instead carried as metrics, as described in the section below.

## Pinpointing the call site: code.* attributes

Every span that this suite creates (`SamplerScope`, `OperationScope`, the manual RabbitMQ publish span, the cycle span of `InfrastructureHealthMetricsStarter`) carries the standard OpenTelemetry `code.function`, `code.filepath` and `code.lineno` attributes, naming the exact method and line that opened it. These are populated via the caller-info attributes of the compiler (`[CallerMemberName]`, `[CallerFilePath]`, `[CallerLineNumber]`), being constants baked in at compile time and not a stack walk or reflection, hence this costs nothing at runtime. `EngineDiagnostics.TagCodeLocation` and `EngineDiagnostics.TagCurrentCodeLocation` hold the shared implementation for `Jube.Engine`, while `OperationScope` in `Jube.Service` carries its own copy of the same shape, since that project does not reference `Jube.Engine`.

This deliberately does not extend to metric tags: `code.filepath` and `code.lineno` are effectively unique per call site, and tagging a metric with them would multiply its cardinality by every place that happens to record it, which is exactly the kind of unbounded tag that this suite has avoided throughout. For a metric, the instrument name plus its existing business tags (stage, area and operation) already narrow matters down close to one call site, and for anything needing more precision than that, the span-level attributes above are the right place to look, not another metric tag.

## Redis and Postgres client-side metrics

`OpenTelemetryMetric` also carries genuine per-command Resp and Postgres client latency, closing a gap in the local capture story: `OpenTelemetry.Instrumentation.StackExchangeRedis` (wired above) produces spans only, with no Meter of its own, and no Npgsql meter is registered with the capture, hence neither would otherwise reach the local table, despite the Resp and Postgres *server-side* tables above already being rich.

- **Redis**: `RespCommandMetricBridge` (`Jube.Engine.Observability`) attaches a second, independent `ActivityListener` to the `ActivitySource` of `OpenTelemetry.Instrumentation.StackExchangeRedis` (the same "listen alongside whatever else is already listening" technique that `OpenTelemetryMetricCapture` uses for Meters) and records the duration of each finished span into `jube.resp.command.count` and `jube.resp.command.duration` on the `Jube.Engine` meter, tagged by command name (`SET`, `GET`, `INCR` and so on) and outcome. Since it rides on the same spans, it inherits the same characteristics: no per-command hot-path cost (harvested on `FlushInterval`, not synchronously), and only populated when `EnableOpenTelemetry` is on (the `ActivitySource` in question is only ever created once `AddRedisInstrumentation` above actually runs).
- **Postgres (command latency)**: `DataDiagnostics` (`Jube.Data.Observability`) wires the trace hook of LinqToDB once, globally, at startup, and unconditionally, independent of `EnableOpenTelemetry`, in the same manner as `OpenTelemetryMetricCapture` itself is unconditional. Every `DataConnection` created afterward (every repository, every service, across the whole codebase, not only the invoke pipeline) is covered automatically, with no change needed per call site. It records `jube.postgres.client.command.count` and `jube.postgres.client.command.duration`, tagged by `TraceInfo.Operation` (`ExecuteReader`, `ExecuteNonQuery`, `ExecuteScalar`, `BulkCopy` and so on, being a fixed enum) and outcome (`ok` or `error`), and never by SQL text, which would carry unbounded cardinality. This complements, rather than replaces, `PostgresMetric`, `PostgresReplicationStatus`, `PostgresIndexStatistics` and `PostgresTableStatistics` above: those see the view of the server (cache hit ratios, replication lag, table bloat), whereas this is the per-command latency of the .NET client.
- **Postgres (connection pool and wire-level)**: `NpgsqlEventCounterBridge` (`Jube.Data.Observability`) closes what `DataDiagnostics` alone cannot see: connection pool exhaustion, bytes actually on the wire, prepared-statement reuse. It was written against the `EventCounters` surface of the `Npgsql` `EventSource`, which was confirmed live at the time to emit `busy-connections`, `idle-connections`, `connection-pools`, `total-commands`, `current-commands`, `failed-commands`, `prepared-commands-ratio`, `bytes-written-per-second`, `bytes-read-per-second`, `commands-per-second`, and (when multiplexing is enabled, which the connection strings of this codebase do not do) three multiplexing-batch averages. A plain BCL `EventListener` matched by `EventSource.Name == "Npgsql"` picks these up with no package reference to Npgsql needed at all, recording each onto the same `Jube.Data` meter as `jube.postgres.client.<name>`, with the three `-per-second` counters (genuine deltas) via `Counter.Add`, and everything else (point-in-time or cumulative-so-far values) via `Histogram.Record`, such that the Min and Max of a per-minute aggregate show the observed range rather than a nonsensical sum. It deliberately does **not** enable the sibling `Npgsql.Sql` source, which carries verbose per-command SQL text, being unbounded cardinality and exactly the kind of raw-statement logging that this suite has avoided everywhere else.

Both bridges above are deliberately named `jube.postgres.client.*` (not `jube.data.*` or anything mentioning Npgsql by name) precisely so that searching `OpenTelemetryMetric` for **`postgres`**, a plain substring match against `MetricName` without regard to case, finds every Postgres client-side metric in one search, from both bridges, rather than needing to know which bridge produced which name. Searching for `npgsql` will find nothing, as the driver itself is an implementation detail, never named in a metric that this suite emits.

## Purging

Every table in this suite accumulates at least one row a minute, indefinitely, unless something purges it. `InfrastructureHealthMetricsPurgeStarter` serves that purpose, being a background loop, separate from the sampling starter above (a different concern, a different cadence and no shared state, mirroring `CachePruneTaskStarter` sitting alongside `ManageCountersStarter` for the same reason), that purges all thirty-eight tables sharing this retention setting once a cycle: the twenty-four browsable via the endpoints listed below, `ApplicationLogEntry`, the three `EntityAnalysisModel*Counter` tables, the Archiver, case-creation and `ModelInvokeWarning` tables covered in [Background Processing Performance](../BackgroundProcessingPerformance/index.html), and four pre-existing counter and balance tables (`HttpProcessingCounter`, `EntityAnalysisAsynchronousQueueBalance`, `EntityAnalysisModelAsynchronousQueueBalance`, `EntityAnalysisModelProcessingCounter`) that predate this suite but share its retention setting. `PostgresIndexStatistics` and `PostgresTableStatistics` are excluded, since those are live catalogue snapshots with no historical rows to purge. `ContainerLogEntry`, the two HAProxy tables and `OverlayNetworkTaskDrift` are purged in the same manner despite being written by the separate `Jube.Monitoring` sidecar process and not by `InfrastructureHealthMetricsStarter`, as purging is a property of the table, not of whichever process happens to write to it.

Retention is configured in the same manner as `SearchKeyCacheServerIntervalType` and `SearchKeyCacheServerIntervalValue` already are elsewhere in this codebase, which is to say a single-letter unit paired with a count:

``` text
InfrastructureHealthMetricsPurgeIntervalType=d
InfrastructureHealthMetricsPurgeIntervalValue=7
```

`d`, `h`, `n`, `s`, `m` and `y` (days, hours, minutes, seconds, months and years) are the accepted unit letters, the same vocabulary that the retention setting of `CachePruneTaskStarter` uses. The cutoff is computed against `DateTime.UtcNow` every cycle, and as this codebase is UTC throughout (there is no `DateTime.Now` call anywhere in `Jube.Engine`, `Jube.Cache` or `Jube.Data`), there is no local-time offset for which to account. The defaults above keep a week.

The purge cycle itself repeats every `WaitInfrastructureHealthMetricsPurge` milliseconds (default `60000`, matching the one-minute sampling cadence of this suite), and the backlog of each table is deleted `InfrastructureHealthMetricsPurgeDeleteLimit` rows at a time (default `1000`, matching the default of `CacheTtlDeleteLimit`) rather than in one unbounded `DELETE`. Postgres has no `DELETE ... LIMIT`, hence this selects one chunk of primary keys older than the cutoff, deletes exactly those, and repeats until a chunk comes back smaller than the limit (it was confirmed live that the `Take().DeleteAsync()` of `LinqToDB` fails outright against Postgres with a syntax error, `ORDER BY` and `LIMIT` on a bare `DELETE` being MySQL and SQL Server syntax and not standard SQL, such that the select-then-delete-by-id shape is the one that actually works). All thirty-eight tables purge concurrently via `Task.WhenAll`, for the same reason that the sampling groups above do: a large backlog on one table (many chunk round trips, for example after the purge job has been off for a while) must never stall every other table behind it.

`EnableInfrastructureHealthMetricsPurge` (default `True`) turns the whole cycle on or off explicitly, rather than relying on `InfrastructureHealthMetricsPurgeDeleteLimit=0` (the `Take(0)` of the loop breaking before any `DELETE` is issued) or an impractically large `WaitInfrastructureHealthMetricsPurge` as an implicit off switch, both of which work as a stopgap, but neither of which says "purging is disabled" to the next person reading the configuration. `PurgeConnectionString` is an optional, separate connection string for this cycle only, falling back to `ConnectionString` when unset, for exactly the same reason that `MigrationConnectionString` exists: the credential of `ConnectionString` is deliberately without DELETE in a hardened deployment (`GRANT SELECT, INSERT, UPDATE ON ALL TABLES` only, no `DELETE`, in `Jube.Cluster/database.sh`), hence without a credential that actually has `DELETE` on these tables every purge attempt fails with Postgres `42501`. That failure is caught per table in `PurgeTableAsync`, logged, and does not stop the purges of the other tables, but it does mean that the retention window above is not actually being honoured, which is easy to miss since nothing else surfaces it. `Jube.Cluster/database.sh` provisions a `jube_purge` user scoped to `SELECT` and `DELETE` on exactly this table list (with no `ALTER DEFAULT PRIVILEGES`, unlike `jube_app` and `jube_reporting`, hence a table added to the purge list later needs its grant added there explicitly) at which `PurgeConnectionString` is to point.

- `GET /api/PostgresMetric`
- `GET /api/RespMetric`
- `GET /api/RespSlowOperation`
- `GET /api/RespConnectionMultiplexerMetric`
- `GET /api/PostgresReplicationStatus`
- `GET /api/RespSentinelStatus`
- `GET /api/RespSentinelEvent`
- `GET /api/RespConnectionEvent`
- `GET /api/RespCallCounter`
- `GET /api/EtcdMemberStatus`
- `GET /api/PatroniMemberStatus`
- `GET /api/EtcdClusterEvent`
- `GET /api/PatroniClusterEvent`
- `GET /api/DockerContainerMetric`
- `GET /api/DockerHostMetric`
- `GET /api/OpenTelemetryMetric`
- `GET /api/OtlpDispatchCounter`
- `GET /api/PostgresLogEntry`
- `GET /api/ContainerLogEntry`
- `GET /api/DockerEvent`
- `GET /api/HAProxyServerStatus`
- `GET /api/HAProxyReachabilityProbe`
- `GET /api/OverlayNetworkTaskDrift`

All twenty-four accept the same optional query parameters, pushed down to the database rather than filtered after the fact:

- **`take`**: the maximum rows to return (default and maximum 100000).
- **`from`** / **`to`**: restrict to a UTC date and time range (`CreatedDate` for the wide snapshot tables, `OccurredDate` for the narrow ones), inclusive at both ends. Each defaults independently to the last 24 hours when omitted, hence a plain call without either returns the samples of the last day rather than the whole table.
- **`search`**: a substring match, without regard to case, against the text-bearing columns that each table has (`Instance` for `DotNetRuntimeMetric`/`PostgresMetric`/`RespMetric`; `Instance` or `ClientName` for `RespConnectionMultiplexerMetric`; `Command`, `CommandName`, `KeyName`, `ClientAddress` or `ClientName` for `RespSlowOperation`; `UserName`, `ApplicationName`, `ClientAddress`, `State` or `SyncState` for `PostgresReplicationStatus`; `EntityType`, `Name`, `Ip`, `Flags` or `MasterLinkStatus` for `RespSentinelStatus`; `Channel` or `Message` for `RespSentinelEvent`; `EventType`, `EndPoint`, `FailureType`, `Message` or `Exception` for `RespConnectionEvent`; `Call` for `RespCallCounter`; `Endpoint`, `Name`, `HealthReason` or `Alarms` for `EtcdMemberStatus`; `Name`, `Host`, `Role`, `State` or `Scope` for `PatroniMemberStatus`; `Endpoint`, `Name`, `EventType`, `PreviousValue` or `NewValue` for `EtcdClusterEvent`; `Scope`, `Name`, `EventType`, `PreviousValue`, `NewValue` or `Reason` for `PatroniClusterEvent`; `Name`, `Image`, `State` or `Status` for `DockerContainerMetric`; `Instance` or `OperatingSystem` for `DockerHostMetric`; `MetricName` or `Tags` for `OpenTelemetryMetric`; `Message` or `Level` for `PostgresLogEntry`; `ContainerName` or `Message` for `ContainerLogEntry`; `EventType`, `Action` or `ActorName` for `DockerEvent`; `Signal` for `OtlpDispatchCounter`; `PxName`, `SvName` or `Status` for `HAProxyServerStatus`; `Target` or `HAProxyAddress` for `HAProxyReachabilityProbe`; `ServiceName` for `OverlayNetworkTaskDrift`).
- **`samplePercentage`**: an unexposed, agent-orientated fourth filter, not present in the toolbar of the user interface and not carried in any form layout metadata. It is a percentage from 0 to 100 (values outside that range are clamped), and each row that already matches `from`, `to` and `search` is included independently with that probability, evaluated on the server side (`random() < samplePercentage / 100.0`, added to the `WHERE` clause of the query itself, not applied by fetching everything and filtering in .NET), such that `samplePercentage=10` returns roughly a random one-tenth of matching rows, not the newest tenth that `take` would otherwise return. It is intended for a baseline-and-compare workflow: an agent takes an unbiased random sample of activity early (say, right after onboarding a new deployment) and later compares recent activity against that stored baseline, which the normal most-recent-first ordering cannot provide on its own since it always returns the same tail end of the table.

All twenty-four are restricted to the landlord tenant (any other caller receives 403), no permission number being involved, and none are scoped to a tenant or Model, as the landlord sees every row, since none of this data is tenant-scoped. Each is also browsable as an area of the **Performance** page under Administration in the user interface, itself offered to the landlord only, where the date range and search are available from a toolbar above the grid, together with Refresh and export, whereas `samplePercentage` works against every endpoint above but is deliberately absent from that toolbar and from the page itself, being reachable only by calling the endpoint directly.
