# Resp Schema

As introduced in the architecture section of this documentation, the real-time performance of the platform is in large part owing to the use of a Remote Key Value \ Data Structure Pair data store, henceforth Resp, which implies any server speaking the RESP protocol (Garnet being the server provided in the Docker Compose file, with Redis being a compatible alternative). A Key Value Pair data store at first pass might appear analogous to a Relational Database Management System (RDBMS). However, given the inability to query, as data can only be accessed via known keys, significant thought needs to be given to schema.

In the Resp Schema set out in Jube, there are three data structures in principal use:

| Data Structure | Use Case                                                                                                                                                                                                                                                                                                                                                                                                                                           |
|----------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Sets           | A structure that given a key maintains a list of values rolling up to a key.                                                                                                                                                                                                                                                                                                                                                                       |
| Sorted Sets    | A structure that given a key maintains a subset of keys preserving a prescribed order.                                                                                                                                                                                                                                                                                                                                                             |
| Hash Tables    | A structure that given a key maintains a large subset of key values rolling up (a key value within a key value). Using Hash Tables over the persistence of this same data in a more traditional key value pair, which would work fine, is thought to be less memory intensive (https://instagram-engineering.com/storing-hundreds-of-millions-of-simple-key-value-pairs-in-redis-1091ae80f74c), while maintaining a slightly more elegant schema. |

## Key structure

The key structure follows a commonplace standard where components of the key are separated with a colon (i.e., :). Key segments uniformly include a tenant identifier immediately following the prefix (e.g., ReferenceDate:1, where 1 is the tenant identifier). Guids are stripped of their hyphens, although this is the only place in the system where that is done.

Upon browsing the keys of a Resp server having processed transactions for the default model, where the tenant identifier is 1, the EntityAnalysisModelGuid is 90c425fd-101a-420b-91d1-cb7a24a969cc and AccountId is a Search Key, it can be seen that the keys are arranged by data structure as follows (the Guids of individual transactions and counters being abbreviated):

```text
Sets
  PayloadJournal:1:90c425fd101a420b91d1cb7a24a969cc:856a59e61a43...
  PayloadJournal:1:90c425fd101a420b91d1cb7a24a969cc:da6c084dc272...
  PayloadJournal:1:90c425fd101a420b91d1cb7a24a969cc:df5ed3c7d0fc...

Sorted Sets
  Journal:1:90c425fd101a420b91d1cb7a24a969cc:AccountId:Test2
  ReferenceDate:1:90c425fd101a420b91d1cb7a24a969cc
  ReferenceDateLatest:1:90c425fd101a420b91d1cb7a24a969cc:AccountId

Hash Tables
  ReferenceDateLatest:1:90c425fd101a420b91d1cb7a24a969cc
  Payload:1:90c425fd101a420b91d1cb7a24a969cc
  PayloadBytes:1
  PayloadCount:1
  PayloadLatest:1:90c425fd101a420b91d1cb7a24a969cc:AccountId
  ReferenceDate:1
  Sanction:1:90c425fd101a420b91d1cb7a24a969cc
  TtlCounter:1:90c425fd101a420b91d1cb7a24a969cc:4d3deb06709a44b...
  TtlCounterEntry:1:90c425fd101a420b91d1cb7a24a969cc:4d3deb06709a44b...
```

In the current release of Jube, Latest values are maintained on a largely informational basis but are reserved for future use in payload reclassification.

The Payload prefix can be subject to compression based on the RespMessagePackCompression environment variable, in which case LZ4 Block Array Compression will be used. While LZ4 compression is extremely fast and introduces only negligible overhead, for a small payload, there is scant compression benefit.

## Other keys and channels

Beyond the structures supporting model invocation set out above, a small number of plain keys are maintained, each being a single value with an expiry, and it can be seen that two of them stand outside the convention of a tenant identifier following the prefix, as they are not particular to a tenant:

| Prefix                        | Type       | Key Structure                                                                                                              | Description                                                                                                                                                                                                             |
|-------------------------------|------------|----------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| ActivationWatcherLastLocation | String     | ActivationWatcherLastLocation:TenantRegistryId:Key:KeyValue | The latitude, longitude and time at which the Key and KeyValue of an activation was last dispatched to the Activation Watcher, retained for 14 days. The KeyValue is truncated to 256 characters.                                             |
| RateLimit                     | Hash Table | RateLimit:RateLimitName:SourceKey                                                                                          | The count of requests for a source inside the window of a named rate limit, the key expiring at the end of the window.                                                                                                  |
| WireReplay                    | String     | WireReplay:Fingerprint                                                                                                     | A marker that an encrypted request envelope has already been received, expiring after the retention period, such that the same envelope cannot be replayed.                                                             |

The Publish \ Subscribe functionality of Resp is used also, on channels that follow the same convention of colon separated segments. The HashSet and HashRemove channels maintain parity of the local LRU cache between instances, and are set out in [Local LRU Cache](../LocalLruCache/index.html). The remaining channels are ActivationWatcher:TenantRegistryId, relaying Activation Rule matches to the Activation Watcher, CallbackSet and CallbackRemove, relaying the responses of asynchronous model invocation between instances, and UserRegistryApiKeySet and UserRegistryApiKeyRemove, relaying changes to API Keys between instances.

## Optional Postgres offload for Hash Table writes

The Hash Table structures above are, by default, all backed by Resp. Setting the RespHsetOffloadToPostgres environment variable to True, it being False by default, redirects Hash Table reads and writes to a Postgres table, CacheSetHash, instead of Resp. This is a global switch across every Hash Table prefix in the table above, rather than a choice for each structure.

CacheSetHash is hash-partitioned by Key into four partitions, with a composite primary key on (Key, Field) and a covering index over (Key, Field) including ByteValue, IntValue and FloatValue, so that point lookups are satisfied entirely from the index without a heap fetch. Byte-array values (serialised payloads and similar) are stored in ByteValue, whereas numeric increments and decrements, the common case for counters, are stored in IntValue or FloatValue and applied as a single atomic statement, as follows:

```sql
INSERT ... ON CONFLICT DO UPDATE SET value = COALESCE(value, 0) + @increment
```

This avoids the chain of casts, from byte array to number and back, that an equivalent of the numeric HINCRBY command would otherwise need were the value stored as serialised bytes.

This is a genuine architectural choice between two backends for the same data, and the right default depends on the relative headroom of Resp against Postgres in the deployment. Benchmarking on representative production hardware is advised before enabling the offload for a production workload, keeping in mind that the benchmarking carried out in development was on a laptop rather than server-grade hardware.

The most common scenario for offloading Hash Tables to Postgres is where memory resources are highly constrained, especially in cloud environments, given an asymmetry between compute provisioning (Jube does not need much) and memory availability (Jube needs a lot in the absence of offloading) in stock images. The trade comes down to a reluctance to pay a premium for RAM, where compute is comparatively cheap. On decent quality SSD's, while response times vary a bit more, the performance degradation is not materially different, and response times tend to be perfectly acceptable (i.e. there is not a deal of difference between a 10ms response and a 30ms response time in practical terms).
