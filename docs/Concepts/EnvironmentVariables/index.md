Environment Variables passed to Jube at startup will override the hardcoded defaults above. Environment Variables are not written to disk in any form, and their contents are available only in the Jube application's memory and operating system session.

The Environment Variable string can be tokenised, and secrets can be swapped in from a file topology at a given path, where the file name is the key and the contents of the file is the value. This approach provides full compatibility with Docker Secrets, which mounts secrets as files using tmpfs (memory-mounted file system). For example, given the token [@RespPassword@], a file called RespPassword and the contents of that file being localhost, the Environment Variable may be passed as RespConnectionString=[@RespPassword@]. At startup the token is detected, extracted and replaced with the contents of the file RespPassword mounted by Docker Secrets. Tokens that resolve are replaced in place; those that do not are left unchanged and an error is written to STDOUT. This approach ensures that only genuinely secret information is stored in Docker Secrets, with more verbose Environment Variable strings being safe to live outside declared secrets, allowing for clearer intent and greater maintainability. Secrets are processed at startup and before logging, with any errors written to STDOUT rather than the logging library.

This mechanism is entirely free-form, which is to say that there is no fixed or hardcoded list of recognised token names anywhere in Jube. Any Environment Variable's string value is scanned for the `[@...@]` pattern, and whatever name appears between the brackets is looked up directly as a file name under `SecretsPath`, keeping in mind that the token name and the Environment Variable it appears in are otherwise unrelated to each other and to any specific secret Jube ships with. It follows that naming a new secret file and referencing it as `[@ThatFileName@]` from any Environment Variable is enough to wire it in, and no code change is needed to add support for a new token.

## Time zone convention

Every timestamp is UTC at rest and UTC through the pipeline, and is turned into the viewer's local time only in the browser. Postgres columns are `timestamp without time zone` holding UTC wall-clock values; the application pins its own process time zone to UTC when `Jube.Data` loads (`UtcTimestampStorage`: it sets `TZ` to `UTC`, clears the cached local zone and turns off linq2db's timestamp normalisation), because the Npgsql driver in use converts `DateTime.UtcNow` to the process-local zone when writing a `timestamp` column, which on a developer machine outside UTC used to shift stored values by the local offset. The API serialises every `DateTime` with a trailing `Z`, and the single page application formats dates and times in the browser's zone. Containers already run in UTC, so production storage was never affected; the convention now holds on any host.

## Build-time variable for the single page application

`VITE_JUBE_WIRE_STAGING_DELAY_MS` (default `1500`) is read when the single page application is built, not at runtime. It is the pause in milliseconds before the browser loads the generated wire decoders after the first wire description arrives. A missing, negative or non-numeric value keeps the default.
