# Datasource Template dialect

The Template display kind (`DatasourceDisplayKind.Template`, 29) lays a datasource's rows out in markup the owner writes, in a deliberately small Vue-style dialect. It is rendered on the server only: `DatasourceTemplate` in `Jube.Service/Charts/Datasource/Template` parses the text and returns an escaped HTML fragment in the card (`Display.Markup`, `MarkupKindId` 2). The browser draws the fragment through `JubeMarkup`, which re-parses it and keeps only the tags and attributes below, so neither side trusts the other and `v-html` is never used. There is no client-side template engine, so there are no shared conformance vectors: the server tests are the specification.

## What a template can contain

- Tags: `div span p h1-h6 ul ol li strong em b i small br hr table thead tbody tfoot tr th td caption section article header footer dl dt dd time code pre abbr mark sub sup`, plus `<template>` as an invisible wrapper for `v-for` and `v-if`. Anything else (`script`, `style`, `a`, `img`, `iframe`, `svg`) is refused with its line and column.
- Attributes: `class title role scope colspan rowspan datetime lang dir`, `aria-*` and `data-*`, written plainly or with a token inside the value (`class="badge [@ row.status @]"`). `id`, `style`, `href`, event handlers and every other `v-*` directive are refused.
- Text interpolation with a token, `[@ expression @]`, the same token the case display templates use. Every value is HTML-escaped, always. Names, members and filters are not case sensitive, so `[@ Rows[0].REGION | UPPER @]` works.
- Directives: `v-for="row in rows"` or `v-for="(row, index) in rows"`, `v-if`, `v-else-if`, `v-else`. `v-for` and `v-if` cannot share an element (wrap in `<template>`); `v-else` must directly follow a `v-if` or `v-else-if` sibling.
- Tokens in attributes: a value that is exactly one token (`class="[@ expr @]"`) is omitted when the result is null or false; a value mixing text and tokens is always written. The old colon binding (`:class`) is refused.

## Names in scope

`rows` (each row an object keyed by column name), `columns` (objects with `name`, `ordinal`, `type`), `rowCount`, `truncated`, and the loop variables. Any other name is a compile error, so `window`, `constructor` and typos are caught as the template is written.

## Expressions

Literals (numbers, `'text'` or `"text"`, `true`, `false`, `null`), member access (`row.total`, `row['order total']`, `rows[0]`, `.length`), `! -`, `* / %`, `+ -`, `< <= > >=`, `== !=` (`===` and `!==` are accepted as the same thing), `&&`, `||`, the conditional `a ? b : c` and parentheses. Numbers are decimal; division by zero and overflow give nothing rather than an error; a missing member gives nothing. `+` adds numbers and otherwise joins text. No calls, assignment or arrow functions exist.

Filters follow a pipe: `number(digits?)`, `percent(digits?)` (a fraction: 0.25 is 25%), `currency('GBP')`, `date`, `dateTime` (UTC, `20 Oct 2026` and `20 Oct 2026 10:30`), `upper`, `lower`, `truncate(n)`, `round(digits?)`, `default(x)` (for null or empty text) and `join(separator?)`. Number and date formats follow the page language.

## Limits

Template text 65,536 characters, element nesting 24, expression nesting 32, 100,000 render steps (each element, text node and loop iteration), 1,000,000 characters of output. Breaching a limit is a coded error that says what to narrow. Rows are capped at 5,000 by the card query, so a loop over `rows` inside a loop over `rows` stops at the step limit.

## Where it surfaces

Introspect (`POST /api/VisualisationRegistryDatasource/Introspect`) returns `TemplateError` with line and column in the page language for the text being typed; Preview and Card return an Error card with the same message when the template fails, and the grid still comes if it is switched on; save refuses an empty or invalid template with a `TemplateText` validation failure. The class names a template uses must exist in the Vue bundle's CSS. Because the server cannot see which utilities a stored template uses, `src/assets/main.css` carries an `@source inline(...)` safelist of text colours that are safe on the page, surfaces, borders, sizes, spacing, layout and the daisyUI components; any other class is kept on the element but has no styling.

## The form dialect

Case workflow forms and displays use the same engine with the form dialect (`TemplateDialect.Form`), compiled by `FormCompiler` and drawn by `TemplateRenderer.RenderForm`. There is no JavaScript and no iframe: the server evaluates the template and sends an escaped fragment, and the browser re-parses it against an allow-list (`TemplateForm.vue`, `templateForm.ts`).

- Extra tags: `form fieldset legend label input select option textarea`. Extra attributes: `name type placeholder value` on `input`, `name` on `select`, `value` on `option`, `name placeholder rows` on `textarea`, `for` on `label` (a field name, not an id). `id`, `style` and event handlers stay refused. Input types are `text number date datetime-local email tel checkbox radio`.
- Names in scope: `Form` (the values entered so far, by field name), `Case` (`Id CaseKey CaseKeyValue Status Priority Created`) and the payload families `Payload Abstraction Dictionary TtlCounter Sanction HttpAdaptation ExhaustiveAdaptation AdvancedAnalyticsAdaptation Activation`. The legacy `[@Payload.Amount@]` spelling is the same expression as `[@ Payload.Amount @]`.
- A field name is a fixed `name` of a letter then letters, digits and underscores (64 at most), unique ignoring case; radio buttons of one name form a single field. A field cannot sit inside a `v-for`. A `select` needs literal `option` values, and radio buttons need literal `value`s; these are the choices the server enforces.
- Showing and hiding is `v-if="Form.reason == 'other'"`. The client posts the values entered so far to `POST /api/CaseWorkflowDisplayExecution/Form`, and the server answers with the fragment, the names of the fields shown and every declared field. A field the template does not show for the submitted values is dropped on submit.
- Submitting (`POST /api/CaseWorkflowFormEntry`) compiles the stored template, rejects any key that is not a field (without echoing it), checks each shown value against its type (`number date datetime-local email tel checkbox`), the choices of a `select` or radio group and the text length limits (4,000, 20,000 for a `textarea`), and stores only the accepted values. A template that does not compile refuses every submission with `FormTemplateInvalid`.
- A display is rendered with the same engine, read only: fields are drawn disabled. A template that does not compile answers 422 with the message in the page language. Legacy display or form HTML that uses tags the dialect does not allow (scripts, styles, links, images) must be rewritten.
- Number filters also accept a number held as text (`'12.5' | number(2)`); comparison never treats text as a number.
- Submitted entries are drawn read only by `POST /api/CaseWorkflowDisplayExecution/FormEntries` for the case's key and key value, newest first (50 at most). Each entry is drawn from its form's **current** template with the stored values filled in and every field disabled; values the template has no field for, or all of them when it no longer compiles, come back as `OtherValues` beside it. Entries of forms the caller's role does not hold, or of cases outside the caller's workflow and status roles, are left out. The Case page shows them in its Forms section.

## Case SQL: forms, displays, macros, actions and statuses draw from rows

A Form, Display, Macro, Action or Status may carry a **SQL** command (`Sql`, edited with the SQL editor on its page, which also tries it against a case id through `POST /api/CaseWorkflowDisplayExecution/TestSql`). It is a single SELECT, run read only for one case with the tenant-scoped table allow-list of the visualisation datasource, 200 rows at most and an 8 second limit, with two bound parameters: `@Id`, the id of the case, and `@CaseKeyValue`. Its rows are the only data a template sees: `rows`, `columns`, `rowCount`, `truncated`, and, in a form, `Form` for the values entered. `Case` and `Payload` are not available in this mode (read the stored payload from the `Case` table's JSON in SQL). A record with no SQL keeps drawing from the case's stored payload as before.

- **Authoring.** Writing or changing a `Sql` needs permission 67, *Author Case Workflow SQL*. Saving checks the SQL against the author's own table access, refuses any parameter other than the two above and any write. At run time the tables are the tenant's, with the submitter's tenant scope but not the submitter's table permissions: the SQL was vetted when it was saved.
- **Forms.** Completing a form runs the SQL first, validates and draws visibility from its rows, and stores a snapshot on the entry: the SQL, the template text and the rows (`CaseWorkflowFormEntry.Sql`, `Template`, `Rows`) beside the submitted values. An entry is drawn from its snapshot, exactly as it was completed. A form whose SQL fails cannot be submitted (`FormSqlFailed`).
- **Email, SMS and HTTP.** Destination, subject, body and endpoint are rendered from the rows with the same `[@ … @]` tokens. An email destination must come out as addresses (at most ten, no line breaks); a subject is stripped of control characters; an email body is HTML-escaped and no longer URL-decoded; an SMS destination must be a telephone number. An HTTP endpoint must name its scheme, host and port literally: tokens may only fill the path and query, are URL-encoded, and a rendered URL whose host, port or scheme differs, or that carries credentials, is refused. A POST body is JSON built from the rows: `source`, `name`, `caseId`, `caseKey`, `caseKeyValue`, `user`, `rows` and, for a form, `values`.
- **Audit.** Every email, SMS or HTTP call a Form, Macro, Action or Status fires is written to `CaseWorkflowDispatch`, whether sent, failed or refused: what was rendered and sent, to where, what answered (HTTP status and correlation id), how it was drawn (payload or SQL) and the rows. `POST /api/CaseWorkflowDisplayExecution/Dispatches` lists them for a case's key. A status move now dispatches after the move is saved.
- **Engine paths.** Case creation (`CaseProcessing`) and automatic escalation (`CaseEscalationStarter`) fire from the engine, which cannot reference the service project where the template engine lives, so they call `CaseStatusNotifier.PrepareAsync`, which uses the `ICaseStatusDispatcher` that `Jube.App` registers in `CaseStatusDispatchRegistry` (`ServiceCaseStatusDispatcher`). With none registered it falls back to the earlier unaudited payload substitution. A status's SQL runs for the case with the tenant's tables without any user's table permissions or role grants (`DynamicSqlTableAccess.BuildTenantAllowedTables`: tenant membership stands in for the user), because the engine has no user. These calls are audited as `Case creation` and `Case escalation`, with the same dispatch record, and an engine-moved case's status SQL sees the case after it has been saved.
